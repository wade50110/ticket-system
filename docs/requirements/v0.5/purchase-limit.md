## 1. 目標與背景

防黃牛第一道業務閘門:限制單一帳號對單一票券的購買數量。原為 v0.5 規劃項(見 ticket-system/CLAUDE.md)。與 rateLimit(請求頻率)、搶票排隊(流量整形)互補:本功能管的是「一個帳號最多買幾張」的**業務額度**。

**核心技術要求:限購檢查必須與庫存扣減同一原子操作**,否則同帳號多請求併發結帳可繞過限額。

## 2. 功能需求

- 票券新增「每帳號限購數」欄位,由 admin 上架/編輯時設定;**未設定 = 不限購**。
- 額度計算基準 =「目前持有數」= 該帳號該票券在 **PENDING + PAID** 訂單中的數量總和;**REFUNDED / CANCELLED 釋回額度**(退了可再買,與「退票後庫存可被再搶」一致)。
- 結帳時原子檢查:`目前持有 + 本次數量 ≤ 限購數`,超限 → **整筆結帳失敗**(409,訊息含票名與剩餘額度),已扣的庫存與額度全部回補。
- 加入購物車 / 更新數量時預先檢查:`目前持有 + 購物車內同票數量(含本次)> 限購數` → 400 擋下並提示(**僅友善提示、不佔額度**,比照現有庫存檢查不預扣的做法;結帳才是權威閘門)。
- 前端:商城票卡顯示「每人限購 N 張」(未設限不顯示);admin 票券表單新增限購欄位;超限錯誤訊息清楚顯示。

## 3. API 規格

無新端點,既有 API 行為變更:

| API | 變更 |
|-----|------|
| `POST/PUT /api/admin/tickets` | request/response 加 `purchaseLimit`(nullable,≥1 的整數) |
| `GET /api/tickets`、`GET /api/tickets/{id}` | response 加 `purchaseLimit` |
| `POST /api/cart`、`PUT /api/cart/{id}` | 超限 → 400「已達限購上限:{票名} 每人限購 {N} 張,你已持有 {m} 張」 |
| `POST /api/checkout` | 超限 → 409「超過限購數量:{票名} 每人限購 {N} 張,你還可購買 {r} 張」,整筆失敗、全額回補 |
| `POST /api/admin/quota/reconcile`(新增,ADMIN) | 額度對帳:以 DB `orders`(PENDING+PAID)彙總值**覆寫**全部 quota key,回 `{"updated": n, "warning": ...}`。維護用(比照 `/api/admin/stock-sync/retry` 的手動觸發風格),是額度錯誤的**唯一收斂機制**。⚠️ **僅可於無結帳流量的維護窗口執行**:讀 DB 快照後無條件覆寫,未與結帳共用鎖,有併發結帳時可能蓋掉剛成立的扣減而造成永久超限(設計審查發現) |

## 4. 資料模型變更

- `tickets` 新增 `purchase_limit`(INT,nullable,null = 不限;驗證 ≥1)。
- Redis 新增額度計數 key:`ticket:quota:{ticketId}:{userId}`(值 = 目前持有數,無 TTL)。
- 額度計數與 Redis 庫存同為正源;重啟重建規則比照 `StockBootstrap`:**`setIfAbsent`,已存在不覆寫**,來源為 DB `orders`(status IN PENDING, PAID)依 (userId, ticketId) 彙總(現階段資料量小,全表彙總可行;量大時再改增量)。
- **注意:`setIfAbsent` 只能重建「不存在的 key」,修不了「存在但值錯的 key」**——錯誤值的收斂一律靠 admin 對帳 API(見第 3 節),不得宣稱靠重啟收斂。
- **額度的所有 Redis 操作一律走 Lua 腳本**:扣減側(檢查+INCRBY)與釋回側(DECRBY 夾 0)都是;釋回時 key 不存在則不動作,DECRBY 後低於 0 一律夾至 0——**quota 值在任何情況下不得為負**(裸 `DECRBY` 對不存在的 key 會建出負值,等於送額度給使用者超買)。

## 5. 邊界情況與錯誤處理

| 情況 | 系統反應 |
|------|----------|
| 同帳號多請求併發結帳同一票 | 限購檢查與庫存扣減合併為**單一 Lua 腳本**(檢查額度→檢查庫存→DECRBY 庫存→INCRBY 額度),回傳碼區分:key 不存在 / 庫存不足 / 超過限購;結帳既有的排序加鎖照舊 |
| 多票結帳其中一張超限 | 整筆 409,已成功扣的前幾筆票**庫存與額度都回補**(擴充既有 rollbackStock 一併回滾額度)。回滾側為兩個獨立操作(先回庫存、再以 Lua 釋回額度),**非原子**:中間態只會讓併發請求短暫誤判(方向保守,不會超賣/超限),列為已知邊界 |
| 退票 / 取消 | 在庫存回補的同一點以 **Lua 釋回額度(夾 0)**;釋回失敗只 log 不中斷(額度偏高、對使用者保守誤擋),由 admin 對帳 API 收斂 |
| admin 調低限購值至低於某帳號既有持有數 | 不追溯(不退票不鎖定),該帳號僅無法再購;剩餘額度顯示為 0 不得為負 |
| admin 清除限購值(設回 null) | 立即不限購;既有 quota key 保留不清(無害,重建時自然收斂) |
| `purchaseLimit` 傳 0 或負數 | 400 驗證錯誤(要不限購請傳 null) |
| Redis quota key 遺失(手動刪除等) | 扣減 Lua 視為 0 起算(寬鬆放行,可能低估持有),由 admin 對帳 API 收斂;釋回 Lua 對不存在 key **不動作、不得建出負值** |
| 崩潰窗口 (a):Lua 扣減後、建 PENDING 訂單前崩潰 | 庫存與額度都虛佔且**無訂單存在**(order-cancel 排程修不到)。庫存側為既有技術債,額度側由 admin 對帳 API 收斂;列入已知邊界不在本功能解決 |
| 崩潰窗口 (b):markRefunded/markCancelled 提交後、額度釋回前崩潰 | 額度虛佔(使用者被保守誤擋),由 admin 對帳 API 收斂 |
| admin 刪除票券 | 比照現有刪 stock key 的做法,**一併清除該票全部 quota key**(`SCAN ticket:quota:{ticketId}:*`),防無 TTL 的 key 長期累積 |
| 購物車預檢的「目前持有數」來源 | 讀 Redis quota key,**不存在視為 0**(與扣減 Lua 同語意) |
| 購物車檢查與結帳檢查結果不一致(先加車後別單成立) | 允許:購物車僅提示,結帳為權威,結帳時以最新持有數判定 |

## 6. 非目標(範圍外)

- 不做跨票券的帳號總量上限、不做身分證/手機驗證等實名制防黃牛。
- 不做 IP / 裝置維度的限購(那是 rateLimit 與未來風控的範疇)。
- 不追溯已超額的歷史持有。

## 7. 驗收條件

- AC-1:admin 可設定/修改/清除 `purchaseLimit`,前台票卡與明細正確顯示。
- AC-2:結帳後持有數 ≤ 限購數恆成立;剛好買滿上限成功,再多 1 張整筆失敗。
- AC-3:超限結帳 → 409、訊息含票名與剩餘額度、已扣庫存與額度全部回補(Redis 值不變)。
- AC-4:未設限購的票券行為與現況完全相同。
- AC-5:同帳號併發多請求結帳同票,最終持有總數不超過限購數(併發測試)。
- AC-6:不同帳號互不影響(A 買滿不影響 B)。
- AC-7:退票後額度釋回,可再購至上限。
- AC-8:訂單取消後額度釋回(依賴 order-cancel;該功能未上線前此條不適用)。
- AC-9:加入購物車/更新數量超限被 400 擋下,訊息正確。
- AC-10:Redis 清空重啟後,額度由 DB 重建(`setIfAbsent`)且與實際持有一致;既有 key 不被覆寫。
- AC-11:額度值在任何情況下不為負:釋回對不存在的 key 不動作,釋回量大於現值時夾至 0。
- AC-12:admin 對帳 API 以 DB 彙總覆寫全部 quota key,能修復人為製造的錯誤值(過高與過低皆可)。

## 8. 測試要求

- Lua 腳本層:足額 / 剛好滿限 / 超限 / 未設限 / quota key 不存在,各回傳碼正確且庫存額度變化原子;**釋回 Lua:正常釋回 / key 不存在不動作 / 釋回量超過現值夾 0**。
- 併發整合測試(需 Redis):AC-5 同帳號併發不超限、AC-6 跨帳號隔離——**這是本功能的核心測試,比照 version0.3.md 路徑 C 的併發驗證手法**。
- 回補路徑:多票結帳部分成功後超限,驗證前幾筆全回補。
- 退票/取消釋回額度;admin 欄位驗證(null / ≥1 / 0 / 負數);admin 對帳 API(修復過高/過低錯誤值);刪票清除 quota key。
- 前端:admin 表單欄位、商城限購顯示、加車超限訊息、結帳超限訊息。
- 跑過後端 `mvn test` 全套與前端 `npm test` 全套。

## 9. 決策紀錄

| # | 問題 | 決定 | 理由 |
|---|------|------|------|
| 1 | 限購規則形式? | 每票券由 admin 設定,未設 = 不限 | 彈性最大:熱門票限 2 張、一般票不限 |
| 2 | 退票後額度釋回? | 釋回(以「目前持有」計) | 與「退票後庫存可再搶」一致,不誤傷正常退票 |
| 3 | 檢查點? | 結帳(權威、原子)+ 購物車(提示、不佔額度) | 比照現有庫存檢查不預扣的分層;體驗與正確性兼顧 |
| 4 | 超限行為? | 整筆結帳失敗,不自動壓量 | 與庫存不足行為一致;壓量會造成金額與購物車不一致的爭議 |
| 5 | 額度正源與原子性 | Redis quota key + 與扣庫存同一 Lua 腳本 | 沿用「Redis 正源 + Lua 原子」既有架構,防併發繞過 |
| 6 | 額度錯誤值的收斂機制(設計審查後修正) | admin 對帳 API 以 DB 彙總覆寫 quota key | 原稿宣稱「靠重啟重建收斂」不成立:`setIfAbsent` 修不了存在但值錯的 key |
| 7 | 釋回操作 Lua 化、夾 0(設計審查後修正) | 釋回走 Lua:key 不存在不動作、低於 0 夾 0 | 裸 `DECRBY` 會對不存在的 key 建出負值,使用者可藉此超買繞過限購 |
